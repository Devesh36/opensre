## Overview

`find_architecture_violations` is a read-only static analysis tool for maintainers. It scans the local repository and returns architecture violations plus atomic refactor task proposals.

The tool does **not** modify code, execute refactors, or create GitHub issues automatically.

| Tool | What it does |
| --- | --- |
| `find_architecture_violations` | Scan repo for dependency, size, shim, and placement violations |
| `propose_github_issues_from_architecture_tasks` | Build GitHub create-issue proposals from scan tasks (read-only) |
| `opensre architecture-scan` | Same scan with deterministic text report (CLI) |
| `opensre architecture-scan propose OWNER REPO` | Scan + build GitHub issue proposals (read-only) |
| `opensre architecture-scan file-issues OWNER REPO` | Scan + propose + create GitHub issues |
| `/architecture-scan` | Same as CLI inside the interactive shell |

## What it checks

1. **Dependency direction** — reuses CI layering rules (`core → surfaces`, `integrations → tools`, etc.) plus core boundary checks (`cli`, `integrations.tracer`, `tools.investigation`, core-domain → integrations).
2. **Oversized files** — flags Python files above a non-blank line threshold (default 500).
3. **Compatibility shims** — detects forwarding-only modules that re-export imported symbols (not constant-only or prompt modules).
4. **Misplaced modules** — finds `@tool` / `BaseTool` subclasses outside `tools/` or `integrations/*/tools/` (framework code under `core/tool_framework/` is excluded), and client/verifier logic under `tools/`.

## Parameters

| Parameter | Type | Default | Description |
| --- | --- | --- | --- |
| `repo_root` | string | checkout root | Optional absolute repository path |
| `max_file_lines` | integer | `500` | Oversized-file threshold (non-blank lines) |
| `include_baselines` | boolean | `false` | Include known baseline dependency debt tracked in CI |

## Example

### CLI or REPL (deterministic report)

```bash
opensre architecture-scan
```

Inside the interactive shell:

```text
/architecture-scan
```

Both print the same `report` text. Add `--json` (CLI) for the full structured payload.

### Propose GitHub issues (read-only)

```bash
opensre architecture-scan propose Tracer-Cloud opensre --task-indices 0
```

REPL:

```text
/architecture-scan propose Tracer-Cloud opensre --task-indices 0
```

This runs the scan and prints GitHub create-issue **proposals** — nothing is filed yet.

### File GitHub issues (mutating)

```bash
opensre architecture-scan file-issues Tracer-Cloud opensre --task-indices 0
```

REPL:

```text
/architecture-scan file-issues Tracer-Cloud opensre --task-indices 0
```

This runs scan → propose → `execute_github_issue_mutation` for each selected task.
Requires GitHub to be configured. Omit `--task-indices` to file an issue for every task.

### Tool / Python API

```bash
uv run python -c "

import json
result = find_architecture_violations(max_file_lines=500)
```

## Filing GitHub issues from scan results

Issue creation is a **separate explicit step**. After reviewing `proposed_refactor_tasks`:

1. `propose_github_issues_from_architecture_tasks` — build create-issue proposals from scan tasks
2. `execute_github_issue_mutation` — execute each approved proposal

Do not auto-file issues from scan output.

## Related CI checks

Local layering enforcement also runs via:

```bash
make check-imports
```

The scanner complements (but does not replace) those CI checks by producing maintainer-friendly refactor task proposals.
